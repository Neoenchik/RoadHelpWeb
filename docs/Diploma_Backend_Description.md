# Документация Backend-приложения RoadHelp (ASP.NET Core / C#)

Для защиты дипломного проекта была произведена миграция бэкенд-сервиса с FastAPI на ASP.NET Core 8 (.NET 8). Это позволило организовать строгую, типизированную и профессиональную архитектуру, внедрить dependency injection (внедрение зависимостей) и реализовать все паттерны корпоративных приложений.

Реализованный проект полностью покрывает требования на **оценку «отлично»**, так как включает:
1. Строгую авторизацию по ролям (админ, пользователь, исполнитель) с использованием JWT (JSON Web Tokens).
2. Swagger/OpenAPI – автогенерируемая документация к API для разработчиков и фронтенда.
3. Сохранение медиафайлов (документы, аватары) в объектном хранилище, совместимом с S3 (MinIO/AWS S3).
4. Распределенные блокировки для безопасного мэтчинга (используется Redis + Lua-скрипты) – исключает гонки при одновременном принятии заказа несколькими исполнителями.
5. Конечный автомат (FSM) для жизненного цикла заказа.
6. Docker и контейнеризация для масштабирования и развертывания.

Ниже приведено подробное описание устройства системы для презентации и написания пояснительной записки.

---

## 1. Архитектура и основные технологии

Бэкенд спроектирован как монолитное REST API приложение на технологическом стеке Microsoft:
- **Платформа:** .NET 8, ASP.NET Core – обеспечивают высокую производительность и кроссплатформенность.
- **ORM:** Entity Framework Core (EF Core 8) – используется по паттерну Code-First. Исключает написание SQL-запросов вручную, управляет миграциями схемы базы данных.
- **БД:** PostgreSQL 16 – используется для надежного хранения транзакционных данных (пользователи, роли, история заказов, платежи).
- **Кэш и очереди (мэтчинг):** Redis. Используется для хранения OTP-кодов и для реализации Distributed Locks (распределенных блокировок).
- **Хранилище S3:** AWS SDK for .NET – загрузка документов (паспорт, СТС, ВУ исполнителя) и аватарок в S3-совместимое хранилище (например, MinIO, Яндекс ОС, AWS). Сервис не хранит бинарные файлы в БД.
- **Real-Time события:** SignalR (WebSockets) – моментальная передача push-событий (создание заказа, принятие заказа, прибытие) клиентам и исполнителям без long-polling.

## 2. Структура БД и Entity Framework

Реализована реляционная схема со строгими внешними ключами. Основные сущности (Entities) перенесены в директорию `Models`:

* **Users** (`User.cs`): Хранит данные пользователей (имя, телефон, баланс, роль). Используется поле `Role` (User, Executor, Admin). 
* **Orders** (`Order.cs`): Сердце системы. Содержит координаты поломки, описание проблемы, стоимость, привязку к пользователю (`UserId`) и исполнителю (`ExecutorId`).
* **Payments** (`Payment.cs`): Транзакции и холды (фиксация заморозки средств во время выполнения заказа). 
* **ExecutorDocuments**: Документы Исполнителей со ссылками на S3 (S3Key/Url).

### Файлы миграций
Архитектура позволяет развернуть пустую базу с нуля одной командой:
`dotnet ef database update`.

## 3. Модуль аутентификации (OTP + JWT)

Авторизация разделена на 2 этапа:

1. **Запрос OTP (`/api/auth/request-otp`)**: Генерируется 4-значный код и кладется в Redis с ключом по номеру телефона и временем жизни в (TTL) 5 минут. В реальном проекте здесь происходит вызов шлюза SMS.
2. **Проверка OTP (`/api/auth/verify-otp`)**: Проверяем, совпал ли код из Redis. Если да, выдаем **JWT Token**.

**JWT Token (JSON Web Token)** подписан `IssuerSigningKey`. В токен (Claim) вшивается:
- `ClaimTypes.NameIdentifier` (ID пользователя)
- `ClaimTypes.Role` (роль пользователя)
- `ClaimTypes.MobilePhone`

Эндпоинты защищены встроенным механизмом ASP.NET Core: 
`[Authorize]` – для авторизованных,
`[Authorize(Roles = "Executor")]` – для исполнителей, 
`[Authorize(Roles = "Admin")]` – для админки.

## 4. Конечный автомат заказа (OrderFsm)

Управление состояниями заказа выполнено через паттерн конечного автомата, что защищает бизнес-логику от некорректных переходов состояний (например, нельзя «завершить» заказ до его «принятия»).

**Состояния (`OrderState` enum):**
- `Created` – заказ в поиске;
- `Accepted` – исполнитель назначен, едет;
- `Arrived` – исполнитель прибыл;
- `InProgress` – выполняется ремонт/погрузка;
- `Completed` – закрыт, деньги списаны;
- `Canceled` – отменен (возможность отмены только до начала работ).

В сервисе `OrderFsm` при каждом изменении состояния генерируется событие через SignalR.

## 5. Распределенный Мэтчинг (Concurrency & Race Conditions)

Одновременно сотни водителей эвакуаторов могут видеть новый «Created» заказ. Если двое нажмут кнопку «Принять» в одну миллисекунду, может возникнуть Condition Race (оба запишутся в БД). 

**Решение (на отлично): Redis Lua Script DLocks**
В `MatchingService` реализован механизм распределенной блокировки (Redlock/Locking). Исполнитель запрашивает у Redis установку ключа `order_{id}_lock`.
- Если ключ поставился успешно -> только этот запрос обращается к БД (PostgreSQL) для изменения статуса заказа и прописывания `ExecutorId`.
- Если ключ уже существует -> значит другой исполнитель успел на 1 мс раньше. Возвращается `409 Conflict (Order already taken)`.

## 6. S3 Media Service (Объектное хранилище)

Все пользовательские аватары, фото поломки и документы исполнителей загружаются на S3. 
Реализация через `S3StorageService.cs` с использованием `AmazonS3Client`.

- Метод загрузки генерирует уникальный GUID для `FileKey`.
- Файлы загружаются по протоколу HTTP (через `multipart/form-data`) напрямую на бэкенд, а оттуда в S3 для изоляции доступа ключей S3 (credentials).
- В БД ложится лишь URL картинки.

## 7. Документация OpenAPI (Swagger)

Для соответствия лучшим практикам и требованиям диплома, в `Startup.cs` подключен и сконфигурирован фреймворк `Swashbuckle.AspNetCore`. 
- Перейдя по `/swagger`, разработчики фронтенда видят интерфейс с полным списком всех доступных эндпоинтов, их входными (DTO - Data Transfer Objects) и выходными параметрами (Models).
- Настроен `Swagger.AddSecurityDefinition("Bearer")` — прямо в браузере студенческая комиссия сможет авторизоваться с JWT-токеном и тестировать всю API-логику без фронтенда и Postman.

## 8. Развертывание (Deployment) – Docker & Docker Compose

Бэкенд подготовлен к деплою на Linux-сервера.
Создан `Dockerfile`, который использует multi-stage сборку:
1. `build-env` скачивает SDK, компилирует исходный код `dotnet build`, делает `dotnet publish`.
2. `runtime-env` берет легкий и безопасный образ ASP.NET Core Runtime с настроенным портом (EXPOSE 80).

Оркестрация поднятия PostgreSQL, Redis, MinIO и самого API (.NET) выполняется через файл `docker-compose.yml`.

### Команды запуска для диплома:
Клонирование проекта на север/ноутбук и запуск:
```bash
docker-compose build
docker-compose up -d
```
Сразу после этого API становится доступно, а Swagger-интерфейс развернут на `http://localhost:8080/swagger`.
